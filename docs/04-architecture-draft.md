# 04. Черновик архитектуры

Основа: паттерны из курса (`5-33 AGENT_PATTERNS_REFERENCE`) — три слоя, единый формат лида + дедуп,
tool-use loop, модель под задачу, память, propose+confirm, логирование стоимости.

## 1. Конвейер (каждый этап — отдельный модуль)
```
[Профиль фрилансера] ──► ICP и оффер
        │
        ▼
 1 DISCOVERY     найти кандидатов (источники, запросы)           код + немного ИИ
 2 NORMALIZE     привести к единому формату Lead, дедуп           код
 3 ENRICH        собрать досье: сайт, карточка, отзывы, цены      агент-исследователь
 4 QUALIFY       оценить 0–100 «подходит ли под мой оффер»        дешёвая модель + правила
 5 DRAFT         написать первое сообщение, с источниками фактов  сильная модель
 6 APPROVE       человек подтверждает/правит (Telegram-бот)       человек
 7 SEND          отправить с лимитами, паузами, чёрным списком    код
 8 CONVERSE      вести диалог, отвечать на вопросы по оффера      агент-диалог
 9 BRIEF         собрать бриф и досье к звонку                    агент-брифинг
10 SCHEDULE      согласовать время, создать событие               код + агент
11 HANDOFF       отправить фрилансеру контакты и карточку         код
12 LEARN         учёт результатов, что работает                   аналитика
```

## 2. Агенты (узкие специалисты)
| Агент | Задача | Инструменты | Модель (класс) |
|-------|--------|-------------|----------------|
| Profile Builder | интервью с фрилансером, сборка профиля, ICP, оффер | чтение/запись профиля | сильная |
| Researcher | досье на лид | fetch_page, search, read_reviews | средняя |
| Qualifier | оценка соответствия | чтение досье, правила | дешёвая |
| Copywriter | первое сообщение и follow-up | чтение досье и профиля | сильная |
| Conversation | диалог с клиентом | чтение досье, запись заметок, предложить слоты | сильная |
| Briefer | бриф и резюме для звонка | чтение переписки | средняя |
Оркестратор — обычный код (очередь задач), а не ИИ.

## 3. Жёсткие ограничения (в коде, не в промпте)
- дневной лимит отправок и паузы между ними;
- чёрный список (отказавшиеся, «стоп», конкуренты, госорганы);
- любой факт в сообщении обязан ссылаться на запись источника;
- отправка запрещена без подтверждения, пока включён режим «ручной»;
- агент не называет цены и не обещает сроки без разрешения профиля;
- глобальный kill switch в боте владельца;
- на любое «не пишите мне» — немедленная пометка и подтверждение.

## 4. Данные (сущности)
`freelancer_profile`, `icp`, `offer`, `source`, `lead`, `lead_fact` (факт + url + дата),
`contact_channel`, `outreach_message` (draft/approved/sent/failed), `conversation`, `message`,
`brief`, `meeting`, `blacklist`, `agent_run` (токены, стоимость, ошибки), `eval_case`.
Мульти-тенантность (`tenant_id`) закладываем сразу ради будущей продажи.

## 5. Интерфейсы
1. **Telegram-бот владельца** (первая версия): утвердить сообщения, получать горячие лиды, команды
   `/stop`, `/stats`, `/leads`.
2. **Веб-дашборд** (потом): воронка, лиды, досье, стоимость. Для него есть готовый handoff
   ([frontend-handoff](reference/frontend-handoff.md): React, Tailwind, shadcn, 4 состояния экрана, токены дизайна).

## 6. Технологии (предложение по курсу)
TypeScript, Node.js на VPS в РФ, Supabase/PostgreSQL (хранение в РФ — проверить хостинг, при
необходимости self-hosted Postgres), Claude API (tool use, prompt caching), grammY/Telegraf для бота,
очередь (pg-boss или BullMQ). Решение по Supabase против self-hosted Postgres зависит от 152-ФЗ.

## 7. Качество и стоимость
- набор evals из реальных 30 лидов прошлого архива (эталон: что мы бы написали);
- метрики: время, стоимость одного лида, доля фактов с источником, доля правок человеком;
- ориентир затрат на лид и месяц **[не оценено]**: считаем на фазе 0 по реальным прогонам.

## 8. Риски архитектуры
Дрейф качества промптов, блокировки каналов, юридические изменения, зависимость от источников данных.
