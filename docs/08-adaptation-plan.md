## 0. Критическая находка: у нашей аудитории нет почты
Ваша прошлая выборка: «компании без сайта» (салоны, автосервисы, мастерские). У них **нет сайта, значит нет и email**.
Друг сам пишет в README orbit: из 70 собранных компаний ни у одной не было адреса, вкладка «Клиенты» превращается в
список для обзвона. Его поиск почты (`sitescan.py`) ищет адрес **на сайте компании**. Без сайта искать негде.
Следствие для вашего решения «канал как у друга (email первым)»:

| Сегмент | Что есть у лида | Рабочий канал |
|---------|-----------------|---------------|
| **A. Без сайта** (ваш прежний архив) | телефон, иногда Telegram/WhatsApp/VK, карточка 2ГИС | **вручную**: агент готовит текст и скрипт, вы отправляете в мессенджер или звоните (как «Открыть чат» у друга) |
| **B. Сайт слабый или устарел** | сайт, часто почта | email по правилам друга, автоматизируем |
| **C. Агентства-партнёры** (SMM, таргет, digital без разработки) | сайт, почта | email; они продают сайты клиентам, вы делаете руками. У друга это вкладка «Партнёры» |

Предложение: фаза 1 строится на **A и C** (A уже ваша привычная, C даёт почту и автоматизацию), B добавляем после.
Это вопрос В6 в 06.

## 1. Целевая архитектура (форк)
Один репозиторий, пакеты по слоям (паттерн «три слоя» из курса). Имена рабочие.
```
src/
  sources/      сменные источники лидов: gis_browser, gis_api (позже), partners_catalogs, manual_import
  enrich/       сайт, контакты (sitescan), DaData, сигналы «нет сайта / слабый сайт / жалобы»
  qualify/      оценка под ваш оффер (сайты), приоритет
  dossier/      НОВОЕ: досье, каждый факт со ссылкой на источник
  draft/        письма и сообщения (промпты свои), запрет выдумок
  send/         проверки, лимиты, прогрев, SMTP; ручная очередь для мессенджеров
  inbox/        IMAP, разбор ответов, цепочка касаний
  funnel/       стадии, карточки, статусы
  brief/        НОВОЕ: диалог, бриф, handoff с досье к звонку
  bot/          Telegram-бот владельца
  tenancy/      НОВОЕ: профиль исполнителя, ключи и лимиты на пользователя (2–3 знакомых)
```
Правило: источник лидов не зависит от остального. Замена 2ГИС-браузера на API или другой источник = новый файл в `sources/`.

## 3. Парсинг 2ГИС браузером: как делаем безопасно для вас
Решение принято (для себя, сначала так). Как устроено у друга: Playwright, один Chromium на процесс, HTTP-прокси
(SOCKS с логином не работает), до 6 страниц по 12 карточек на пару «рубрика × город», разбор текста карточек
регулярками, а не классами (классы обфусцированы). Ограничения и последствия:
- **Нужен российский мобильный прокси** (платный): датацентровые адреса 2ГИС банит. Свой прокси покупаем сами,
  **ключи друга не используем** (они уже были в архиве, ему нужно сменить пароль).
- Скорость 40–50 с на страницу выдачи, ~1 из 4 загрузок падает по таймауту. Это штатно.
- Телефоны скрыты за кнопкой «Показать телефон»; их раскрывает отдельный шаг.
- Отзывы читаются только через браузер (в официальном API текстов отзывов нет).
- Ломается при смене вёрстки 2ГИС. Закладываем: тест на «выдача не пустая», оповещение в бот, быстрый фикс селекторов.
- Меры, которые закладываем в код сразу: умеренный темп, лимит объёма на прогон, остановка при капче/блокировке,
  хранение только публичных деловых данных, срок хранения, кнопка удаления. Источник сменный (п.1).

## 4. Что строим сами (ядро ценности)
1. **Профиль исполнителя**: услуги, ниши, цены от/до, примеры работ, голос, запреты. Читается промптами.
2. **Досье**: таблица `lead_fact` (факт, URL источника, дата). В сообщение попадают только факты с источником.
3. **Бриф и handoff**: после согласия на созвон агент собирает вопросы по задаче, сроки, бюджет, шлёт вам карточку:
   контакты, досье, бриф, предложенное время, 3 вопроса к звонку.
4. **Мультипользовательность** (вы + 2–3 знакомых): `tenant_id`, отдельные ящики, лимиты, ключи; Postgres.
5. **Оценка качества (evals)**: 30 лидов прошлого архива как эталон, прогон при каждой правке промптов.

## 7. Риски плана
1. Вёрстка 2ГИС меняется: источник нужно сопровождать. Митигация: тесты, сменный источник, API как запасной.
2. Блокировка прокси или IP: темп, пул прокси.
3. Репутация домена при рассылках: прогрев, лимиты, отдельный домен.
4. Юридические риски 38-ФЗ и 152-ФЗ: прозрачность письма, строка отказа, чёрный список, срок хранения.
5. Дрейф качества текстов: evals и ручной просмотр первых 50 писем.
6. Сложность форка: код друга большой (≈1,3 МБ). Берём слоями, каждый слой с тестами.
