## 1. Что это

> **В проекте ДВА режима.** Клиентский (2ГИС → лиды-клиенты с жалобами на связь) и **partners**
> (`parser partners` → агентства-партнёры из каталогов + сбор их email с сайтов; добавлен 30.07.2026,
> подробно в README раздел 10). Ниже операционные заметки относятся к обоим, если не указано иное.


Инструмент ищет в 2ГИС организации, которым в свежих отзывах жалуются на связь
(«не дозвониться»), обогащает их ИНН/руководителем (DaData), оценивает платёжеспособность
и отдаёт как тёплые B2B-лиды в Telegram-бота. Полностью описано в `README.md`.

Стек: Python 3.12, Playwright (Chromium) + мобильный прокси, httpx, pydantic, loguru.
Точка входа: `parser bot` (Telegram) или `parser search …` (CLI).

## 2. Текущее развёртывание

- **Сервер:** Timeweb VPS, Ubuntu 24.04, **2 ГБ RAM — ОБЩИЙ** (на нём же крутятся другие
  боты владельца: chernova, wb_*, postgres, redis, VPN). Это временный сервер для теста.
- **Запуск:** systemd-юнит `leadgen-bot.service`, автозапуск + рестарт при краше +
  **лимит памяти `MemoryMax=1400M`** (чтобы Chromium не уронил соседние сервисы).
- **Пути:** на текущем (временном) сервере проект лежит в **`/root/leadgen`** — юнит там
  правился руками. Эталонный юнит `deploy/leadgen-bot.service` рассчитан на **`/opt/leadgen`**:
  на новом сервере ставь в `/opt/leadgen` как в `deploy/DEPLOY.md`, либо поправь
  `WorkingDirectory`/`ExecStart` в юните под свой путь — это единственные два места.
- **Планируется переезд** на новый выделенный (пустой) сервер — там можно снять ограничения.
- Логи: `journalctl -u leadgen-bot -f`. Рестарт: `systemctl restart leadgen-bot`.

## 3. ⚠️ Что сейчас НАМЕРЕННО занижено (и как поднять)

### 3.1 Мощность фонового сбора — снижена
Сервер общий и слабый, поэтому коллектор идёт **бережно**: короткие пачки + длинный кулдаун
(между пачками браузер закрывается и память освобождается).

Сейчас в коде/`.env` (значения по умолчанию):
```
COLLECT_PER_QUERY=5      # мест за одну пачку
COLLECT_DELAY=25.0       # кулдаун между пачками, сек
```
**На новом сервере — поднять мощность** (в `.env`, затем `systemctl restart leadgen-bot`):
```
COLLECT_PER_QUERY=20
COLLECT_DELAY=3.0
```
Это ускорит наполнение базы в разы. `COLLECT_TARGET` — до скольких лидов копить (по умолч. 100).

> Параллелизм: сейчас **строго 1 Chromium на процесс** (модульный `asyncio.Semaphore(1)` в
> `providers/browser.py`) — защита от OOM. Для параллельного парсинга (несколько браузеров)
> нужен код-change + больше RAM + несколько прокси. См. п.4 и Roadmap в README.

### 3.2 Таймаут браузера — повышен под прокси
`BROWSER_TIMEOUT=60` (сек). Через мобильный прокси страницы 2ГИС грузятся медленно; при 20с
добор падал (0/4). На быстром прокси можно снизить до ~30.

## 4. ⚠️ Прокси — узкое место, нужен лучше

**Зачем вообще:** с датацентр-IP сервера 2ГИС банит браузерный парсинг. Поэтому браузер
ходит через **мобильный RU-прокси** (`PROXY_URL` в `.env`). Сейчас это **один** мобильный
прокси (~1000 ₽/мес, безлимит трафика, ротация IP каждые 5 мин).

**Ограничения текущего прокси:**
- один поток IP → парсинг фактически последовательный;
- бывает медленно/нестабильно (отсюда `BROWSER_TIMEOUT=60` и ретрай карточки);
- при агрессивном темпе — риск бана этого IP.

**Что нужно для масштаба (приоритет для разработчика):**
1. **Прокси получше / пул из нескольких** мобильных или резидентных RU-прокси.
   **Пул уже поддержан в коде:** `PROXY_URL` принимает несколько прокси через запятую,
   `providers/browser.py::ProxyPool` ротирует их и перезапускает браузер после серии сбоев
   (`_PROXY_SWITCH_AFTER`). Осталось только купить каналы и вписать их в `.env`.
   Параллельные браузеры (>1 Chromium) — отдельная задача: снять семафор `_BROWSER_SLOT` и дать
   каждому браузеру свой прокси; требует больше RAM.
2. **Детект бана уже есть** (частично): если у всех карточек 0 телефонов — бот шлёт
   предупреждение «возможно, 2ГИС блокирует прокси». Стоит развить (капча-детект по HTML).
3. Формат строки прокси для `.env`: `PROXY_URL=http://ЛОГИН:ПАРОЛЬ@ХОСТ:ПОРТ` (**HTTP**, не
   socks5 — Chromium не умеет socks5 с авторизацией). Проверка: `parser proxy-check`.

## 5. Жизненный цикл данных — когда база чистится

Всё состояние — в каталоге **`output/`** (переживает `systemctl restart` и обновление кода;
в архив деплоя НЕ входит, т.е. при заливке нового кода данные на сервере сохраняются).

| Файл | Что это | Когда РАСТЁТ | Когда ЧИСТИТСЯ |
|---|---|---|---|
| `output/leads_base.json` | **База горячих лидов** (JSONL, дедуп по ИНН) | **только при фоновом сборе** (разовый поиск шлёт лиды в чат и выгрузку, в базу их НЕ пишет) | **только командой `/clearbase`**. Автоматически — НИКОГДА |
| `output/seen_leads.json` | **Журнал проверенных** организаций (чтобы не выдавать дважды) | при каждом успешном прогоне/сборе | командой `/reset` **или** `/clearbase` |

**Ключевое про дедуп и очистку:**
- **База сама по себе не чистится** — она только копит и дедуплит (одна фирма из разных
  ниш/городов = один лид, ключ = ИНН → source_url → имя+адрес).
- `/reset` — сбрасывает **журнал проверенных** (перескан тех же мест), **база лидов остаётся**.
- `/clearbase` — **полный сброс**: чистит и базу, и журнал, останавливает текущий сбор → сбор с нуля.
- Вручную на сервере: `rm /root/leadgen/output/leads_base.json` (и/или `seen_leads.json`).
- Карточки, упавшие по таймауту прокси, в журнал НЕ пишутся → перепроверятся позже (лид не теряется).

Команды бота целиком — в `README.md` (раздел «Команды») и в меню бота (`setMyCommands`).

## 6. Разработка и обновление сервера

**Локально:**
```bash
python3.12 -m venv .venv
.venv/bin/pip install -e '.[browser,enrich,partners,dev]'   # dev = pytest
.venv/bin/playwright install --with-deps chromium
.venv/bin/python -m pytest -q          # 138 тестов
.venv/bin/parser proxy-check           # проверить прокси
.venv/bin/parser bot                   # запустить бота локально
```
Editable-install: правки в `parser/*.py` подхватываются без переустановки.

**Обновить сервер (залить новый код):**
```bash
# на машине разработчика: собрать архив без .venv/output и залить
# --exclude=.env ОБЯЗАТЕЛЕН: иначе распаковка перезапишет серверный .env локальным
# (с другими ключами/прокси) и бот молча начнёт работать не с теми настройками.
tar --exclude=.venv --exclude=output --exclude=__pycache__ --exclude=.env -czf leadgen.tar.gz leadgen
scp leadgen.tar.gz root@СЕРВЕР:/root/
# на сервере:
systemctl stop leadgen-bot && cd /root && tar -xzf leadgen.tar.gz && systemctl start leadgen-bot
```
Данные в `output/` при этом сохраняются. Первый деплой с нуля — по `deploy/DEPLOY.md`.

**Важно:** ключи/прокси меняются в `.env` **на сервере**, затем `systemctl restart leadgen-bot`.
Секреты в git не коммитятся (`.gitignore`).

## 9. Честные пределы (чтобы не удивляться)

- Тексты отзывов — только через браузер; платный API 2ГИС их НЕ даёт.
- Личный телефон владельца не отдаёт ни один легальный источник (152-ФЗ) — максимум ИНН + ФИО.
- ИНН матчится у ~72% (бренды-домены/латиница не матчатся в DaData).
- Прокси обязателен для сервера — иначе 2ГИС банит датацентр-IP.
- Технические грабли (антибот 2ГИС, ловушка с ИНН Сбербанка на карточке 2ГИС, матчинг DaData) —
  задокументированы в комментариях соответствующих модулей.

## 10. Режим partners — заметки для разработчика

- **Запуск:** `parser partners --niche all --max 50` (или `--urls "…,…"`, `--no-enrich`).
- **Зависимость:** `pip install -e '.[partners]'` (selectolax). Без неё обход сайтов не поедет.
- **Каталоги:** `providers/catalogs.py::CATALOG_PARSERS` — ratingruneta (данные в `__INITIAL_STATE__`,
